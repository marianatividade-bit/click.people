O Produto

O que é o Click.People

Plataforma interna de gestão de pessoas da Clicksign. Substitui planilhas e e-mails no processo de avaliação de desempenho. Construída do zero pela área de People, com auxílio de IA.

O que já funciona hoje

  • Login via Google SSO — só e-mails @clicksign.com têm acesso
  • Ciclo completo de avaliação 360° — rascunho → indicações → validação → avaliação → calibração → encerrado
  • Configuração de perguntas por ciclo (escala, texto, múltipla escolha)
  • Indicação de pares com validação pelo RH
  • Plano de avaliadores gerado automaticamente pela hierarquia (chapter + stream manager)
  • 9-Box visual com eixos e limiares configuráveis
  • PDI (Plano de Desenvolvimento Individual)
  • Plano de Recuperação
  • Feedbacks entre colaboradores
  • Notificações in-app com badge de não lidas
  • Admin de colaboradores e cargos (restrito ao RH)
  • Controle de acesso por papel: hr_admin, business_partner, manager, employee
Próximos passos

O que o time de engenharia precisa fazer

  • 1
    Revisão de código — o time olha o que foi construído e valida a arquitetura
  • 2
    Ambiente na AWS — subir o app em um servidor (já usamos AWS na Clicksign)
  • 3
    Banco em produção — migrar de SQLite para PostgreSQL (possivelmente via Supabase)
  • 4
    Credenciais seguras — configurar variáveis de ambiente do Google OAuth no servidor
  • 5
    Domínio interno — ex: people.clicksign.com
  • 6
    Deploy automático (CI/CD) — código no GitHub → vai pro servidor automaticamente

Supabase

O que é o Supabase: é onde os dados vão ficar em produção. Funciona como um banco de dados PostgreSQL com painel visual — dá pra ver todas as avaliações, dados de colaboradores e resultados direto lá, sem passar pela interface do sistema. Por isso o acesso precisa ser controlado.

  • Q4
    "Já temos uma conta Supabase na Clicksign? Posso criar um projeto separado, exclusivo para o Click.People?"
    Dados de RH precisam estar isolados de outros sistemas.
  • Q5
    "Para fazer o deploy, o time de engenharia precisa ter acesso direto ao banco, ou só a string de conexão é suficiente?"
    Quero que o time configure sem ver os dados.
  • Q6
    "Posso ser a administradora do projeto no Supabase, com acesso restrito só para mim e mais uma pessoa do RH?"

Privacidade e acesso aos dados

Contexto: avaliações de desempenho são dados sensíveis de RH. Ninguém fora do RH pode ter acesso — nem por meio do banco de dados, nem pela AWS. Isso não é desconfiança do time, é compliance e boa governança.

  • Q7
    "Quem na Clicksign vai ter acesso ao ambiente AWS onde o Click.People vai rodar?"
    Quem acessa o servidor pode acessar os dados.
  • Q8
    "Tem como registrar (logar) quem acessa o ambiente e o banco de dados, e quando? Precisamos de auditoria para dados de RH."
  • Q9
    "Podemos combinar que o time de engenharia tem acesso para deploy e manutenção, mas sem permissão para ler os dados das avaliações?"
    É tecnicamente possível separar acesso à infra de acesso aos dados.

Privacidade

As três camadas de acesso aos dados

Já protegido Camada 1 — Interface do sistema
Cada papel vê só o que pode ver. Colaborador não vê avaliação do colega. RH vê tudo. Isso já está construído no código.
Precisa definir Camada 2 — Banco de dados (Supabase)
Quem tem acesso ao Supabase vê todos os dados brutos, sem passar pela interface. Precisa restringir o acesso ao painel a apenas o RH.
Precisa definir Camada 3 — Infraestrutura (AWS)
Quem tem acesso ao servidor na AWS pode acessar tudo. Precisa acordar quem terá esse acesso e garantir registro de auditoria.
